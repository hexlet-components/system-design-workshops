# Шпаргалка по системному дизайну: Архитектура распределенного объектного хранилища s3

Эта шпаргалка содержит ключевые архитектурные концепции, формулы нагрузочных расчетов, низкоуровневую спецификацию хранения чанков на диске и каталог антипаттернов для воркшопа по проектированию распределенного объектного хранилища **s3**.

---

## 1. Сводная матрица архитектурных концепций

| Концепция / Паттерн | Назначение в s3 | Принцип работы | Практические ограничения и компромиссы |
| :--- | :--- | :--- | :--- |
| **Database-per-Service** | Полная изоляция данных сервисов `s3-bucket-service` и `s3-metadata-service`. | Каждый сервис владеет собственной СУБД (`s3_bucket_db`, `s3_metadata_db`). Прямые межсервисные SQL JOIN строго запрещены. | Требует асинхронной дубликации или event-driven интеграции при необходимости связывания данных. |
| **Transactional Outbox** | Исключение аномалии Dual Write при создании/удалении объектов. | События (`ObjectCreated:Put`, `ObjectRemoved:Delete`) записываются в таблицу `outbox_events` в рамках единой ACID-транзакции с метаданными. | Увеличивает размер WAL-лога PostgreSQL и требует процесса вычистки обработанных строк. |
| **CDC (Debezium Engine)** | Бесконтактное считывание событий из таблицы Outbox в Kafka. | Чтение байт журнала предзаписи PostgreSQL WAL (`pgoutput`) и трансляция в Kafka с задержкой < 100 мс. | Зависание Debezium приводит к накоплению WAL-сегментов на диске и рискам исчерпания памяти. |
| **Partition Key Hash** | Сохранение хронологического порядка жизненного цикла файла S3. | Вычисление ключа партиционирования по формуле `hash(bucket_name + "/" + object_key)`. | Риск возникновения "горячих партиций" при массовом сбросе файлов в один бакет с одинаковым префиксом. |
| **Distributed Lock (SETNX)** | Дедупликация и защита от race conditions при Multipart Upload. | Атомарная фиксация `idempotency_key = hash(bucket + key + etag)` в Redis Cluster с TTL = 30-60 сек. | Требует тщательного выбора времени жизни блокировки (TTL) во избежание Thundering Herd effect. |
| **Dead-Letter Queue (DLQ)** | Изоляция поврежденных сообщений (Poison Pills). | При превышении 5 попыток обработки событие перенаправляется в топик `s3.metadata.events.dlq`. | Требует наличия отдельных инструментов SRE-аудита и CLI для ручного или автоматического Event Replay. |
| **Stream Processing (Flink)** | Потоковый пересчет квот бакетов и подсистема Rate Limiting. | Агрегация объемов завантаженных байт во временных окнах (Tumbling/Sliding Event-Time Windows). | Задержка синхронизации Watermark при расхождении часов на нодах может давать временные погрешности квот. |
| **ReplacingMergeTree (OLAP)** | Хранение аудита и аналитика использования без нагрузки на OLTP. | Потоковая батчевая загрузка из Kafka в ClickHouse со сжатием колонок алгоритмом ZSTD (15x). | Запись мелких единичных строк вместо батчей приводит к ошибке `Too Many Parts` в ClickHouse. |

## 2. Шпаргалка по нагрузочным расчетам и формулам

### 2.1. Расчет полосы Change Data Capture (CDC)
$$\text{WAL CDC Bandwidth} = \text{Write RPS} \times \text{Outbox Event Size}$$
* **Входные данные**: 5 000 Metadata Write RPS, размер конверта события = 500 байт.
* **Расчет**: $5000 \times 500\text{ B} = 2\,500\,000\text{ B/sec} \approx 2.5\text{ МБ/сек}$ (или $\approx 20\text{ Мбит/с}$).

### 2.2. Определение числа партиций Kafka
$$\text{Partitions Count} = \max\left(\frac{\text{Total Write RPS}}{\text{Single Partition Max RPS}}, \text{Target Consumer Replicas}\right)$$
* **Расчет**: 5 000 RPS / 208 msgs/sec per partition = **24 партиции** в топике `s3.metadata.events`.

### 2.3. Расчет оперативной памяти Redis Cluster (Idempotency TTL)
$$\text{Redis RAM} = \text{Write RPS} \times \text{TTL (seconds)} \times \text{Key Size}$$
* **Входные данные**: 5 000 RPS, TTL = 1 час (3 600 сек), размер ключа = 128 байт.
* **Расчет**: $5000 \times 3600 \times 128\text{ B} = 2\,304\,000\,000\text{ B} \approx 2.3\text{ ГБ RAM}$.

### 2.4. Расчет дискового объема ClickHouse OLAP (ZSTD Compression)
$$\text{Daily Storage} = \frac{\text{Daily Events} \times \text{Event Size}}{\text{Compression Ratio}}$$
* **Входные данные**: 432M событий/день (5 000 RPS * 86 400 сек), размер 500 байт, сжатие ZSTD 15x.
* **Расчет**: $(432 \times 10^6 \times 500\text{ B}) / 15 = 216\text{ GB} / 15 = 14.4\text{ ГБ/день}$ ($\approx 5.25\text{ ТБ/год}$).

## 3. Физический слой хранения чанков (Chunk Storage Engine)

### 3.1. Чанкирование и Consistent Hashing
* **Фиксированный размер чанка**: Файлы нарезаются на чанки по **64 МБ**. Каждая часть получает `chunk_id = SHA-256(chunk_bytes)`.
* **Consistent Hash Ring**: Хэш `Murmur3(chunk_id)` определяет первичную ноду (Primary Storage Node) и две резервные ноды (Secondary Replicas).

### 3.2. Репликация и Rack-Awareness
* **Фактор репликации**: $RF = 3$. Подтверждение записи (ACK) возвращается клиенту только после успешного сохранения чанка на все 3 ноды.
* **Учет топологии**: Primary и Secondary ноды размещаются в разных серверных стойках (Racks) для исключения отказа при падении коммутатора.

### 3.3. POSIX Иерархия на файловой системе (`O_DIRECT`)
Запись выполняется в режиме `O_DIRECT / O_DSYNC` в обход Page Cache Linux во избежание latency spikes:

```text
/data/s3chunks/
├── 4a/
│   └── 8f/
│       ├── 4a8f9c12b7...d3.dat   <-- Тело чанка (64 МБ бинарных данных)
│       ├── 4a8f9c12b7...d3.meta  <-- Заголовок (CRC32C per 64 KB, ETag, timestamp)
│       └── 4a8f9c12b7...d3.wal   <-- Append-only журнал предзаписи
```

### 3.4. Защита от Bit Rot (Integrity Scrubbing)
* **Поблочный CRC32C**: Каждые 64 КБ данных чанка снабжаются контрольной суммой в `.meta`.
* **Scrubber Demon**: Фоновый процесс сверяет CRC32C с диска и при тихой деградации байт (`CORRUPTED`) автоматического восстанавливает файл с сопредельной реплики.

## 4. Каталог антипаттернов микросервисной архитектуры

### 4.1. Shared Database (Общая база данных)
* **В чем ошибка**: Использование одной схемы PostgreSQL разными сервисами (`s3-bucket-service` и `s3-metadata-service`).
* **Почему возникают проблемы**: Неявная связность на уровне таблиц, блокировки строк, невозможность независимого масштабирования и проведения миграций.
* **Как правильно**: Реализовать паттерн *Database-per-Service*. Сервисы общаются строго через REST/gRPC или события Kafka.

### 4.2. Distributed Monolith (Распределенный монолит)
* **В чем ошибка**: Разделение монолита на сервисы с сохранением цепочек синхронных HTTP/gRPC вызовов при обработке одного запроса.
* **Почему возникают проблемы**: Каскадные сбои (Cascading Failures), суммирование задержек сетевых прыжков (N+1 Network Hops) и падение общей доступности системы ($Availability = A_1 \times A_2 \times A_3$).
* **Как правильно**: Перевести межсервисные интеграции на асинхронный событийный поток (Event-Driven Architecture) с Outbox и Kafka.

### 4.3. Dual Write (Двойная запись в коде)
* **В чем ошибка**: Последовательная запись метаданных в PostgreSQL `COMMIT` и вызов `kafkaProducer.send()` из кода приложения.
* **Почему возникают проблемы**: При сбое сети между коммитом в БД и вызовом Kafka событие теряется навсегда. Система становится рассинхронизированной.
* **Как правильно**: Использовать *Transactional Outbox Pattern* совместно со считыванием WAL через Debezium CDC.

### 4.4. Entity Services (Анемичные сервисы-сущности)
* **В чем ошибка**: Создание сервисов вокруг мелких CRUD-сущностей (`s3-object-key-service`, `s3-etag-service`).
* **Почему возникают проблемы**: Высокий оверхед на сериализацию/десериализацию, отсутствие четких бизнес-границ и размывание логики домена.
* **Как правильно**: Группировать сервисы вокруг целостных доменных контекстов (Bounded Contexts) на основе принципа *Common Closure Principle (CCP)*.

### 4.5. Cyclic Dependencies (Циклические зависимости)
* **В чем ошибка**: Ситуация, когда `s3-bucket-service` вызывает `s3-metadata-service`, а тот обратно запрашивает `s3-bucket-service`.
* **Почему возникают проблемы**: Deadlocks на уровне вызовов, невозможность развертывания сервисов по отдельности и усложнение отладки.
* **Как правильно**: Разрывать циклы через введение асинхронных событий или выделение общего третьей доменного сервиса.

### 4.6. Ignore Backpressure & Poison Pills
* **В чем ошибка**: Попытка бесконечного повтора (infinite retry) поврежденного сообщения без отправки в DLQ.
* **Почему возникают проблемы**: Зависание воркеров (Consumer Group lag), забивание памяти и полная остановка обработки очереди событий.
* **Как правильно**: Настраивать лимит повторов (5 retries) с экспоненциальной задержкой и сбросом сообщения в *Dead-Letter Queue (DLQ)*.
