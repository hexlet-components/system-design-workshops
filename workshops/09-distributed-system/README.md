
## 1. Контекст

Разбираемая в уроке система **s3** начинала свое развитие как монолитная платформа хранения данных. Изначально единое приложение-монолит обрабатывало весь цикл работы с объектами: выполняло аутентификацию клиентов, управляло ACL бакетов, принимало HTTP PUT/GET запросы, сохраняло метаданные файлов в PostgreSQL БД, нарезало файлы на чанки для файлового хранилища и отправляло уведомления об изменениях объектов (`ObjectCreated`, `ObjectRemoved`) во внешние очереди сообщений.

С ростом нагрузки и объема данных монолитная архитектура столкнулась с проблемами.
* **Аномалия Dual Write:** При попытке одновременного обновления метаданных объекта в БД и отправки события в брокер, сбои сети приводили к рассогласованию: метаданные объекта сохранялись, но внешние сервисы-потребители не получали уведомлений.
* **Блокировки СУБД:** Таблицы метаданных и бинарных чанков находились в одной БД. Нагрузка от чтения мелких файлов и записи крупного потока чанков блокировала транзакции метаданных.
* **Высокая связность (High Coupling):** Изменение логики валидации ACL бакетов требовало пересборки и перезапуска всего монолита, отвечающего за отдачу бинарных данных.

Для решения этих проблем в данном уроке проектируется разделение монолита на автономные микросервисы с четким распределением бизнес-доменов и владением данными (Database-per-Service).

## 2. Легенда

### Контекст проектируемой системы
Платформа **s3** - это абстрактное высоконагруженное распределенное объектное хранилище (Distributed Object Storage), предназначенное для надежного сохранения неструктурированных данных (файлов, медиа, бэкапов), управления их метаданными и обеспечения событийно-ориентированной интеграции с внешними системами.

### Исходные требования

#### Функциональные требования (Functional Requirements — FR)
* **FR-1 (Object & Metadata Lifecycle):** Гарантированное создание/удаление бакетов и загрузка объектов (`PUT /bucket/object_key`, `GET`, `DELETE`) с записью версий метаданных и контрольных сумм (ETag/MD5) без аномалий Dual Write.
* **FR-2 (Multipart Upload Support):** Поддержка составной загрузки крупных объектов по чанкам (Init, Upload Part, Complete, Abort).
* **FR-3 (Event Notifications & Outbox):** Гарантированная генерация доменных событий изменений объектов (`ObjectCreated:Put`, `ObjectRemoved:Delete`) через транзакционный журнал (Transactional Outbox) с нулевой потерей сообщений (Zero Data Loss).
* **FR-4 (Idempotent Event & Request Processing):** Дедупликация повторных запросов на уровне API и гарантированно однократная обработка доменных событий (Idempotency) на стороне воркеров.
* **FR-5 (Event Streaming & Audit):** Публикация событий в распределенный журнал событий для последующей асинхронной обработки внешними подписчиками и аналитическими системами.

#### Нефункциональные требования (Non-Functional Requirements — NFR)
* **NFR-1 (Нагрузка & Пропускная способность):**
  * Номинальный поток записи метаданных = 5 000 Write RPS.
  * Номинальный поток чтения метаданных = 25 000 Read RPS.
  * Пиковый трафик данных = до 10 ГБ/сек.
* **NFR-2 (Надежность & Согласованность):** RPO = 0 для транзакций метаданных и Outbox-событий (ACID + WAL CDC).
* **NFR-3 (Задержки p99):**
  * Проверка авторизации и ключей в API Gateway < 5 мс.
  * Фиксация метаданных объекта в Outbox < 15 мс.
  * End-to-End задержка доставки событий CDC в брокер < 100 мс.
* **NFR-4 (Объем данных):** Прирост метаданных объектов ~500 байт на запись. Месячный объем записей метаданных ~13 млрд объектов (~6.5 ТБ метаданных/месяц).

## 4. Глоссарий (Glossary)

* **Bucket (Бакет):** Логический контейнер верхнего уровня в платформе **s3** для изоляции объектов, применения политик доступа (ACL), квот и конфигураций жизненного цикла.
* **Object Key (Ключ объекта):** Уникальный строковый идентификатор объекта в пределах конкретного бакета (например, `images/2026/avatar.png`).
* **ETag (Entity Tag):** Хеш-сумма (обычно MD5) содержимого объекта, используемая для проверки целостности данных при передаче и хранении.
* **Object Manifest (Манифест объекта):** Запись метаданных в `s3-metadata-service`, описывающая размер файла, ETag, версию, владельца, а также список физических идентификаторов чанков в `s3-blob-storage-service`.
* **Multipart Upload Session:** Механизм параллельной или пошаговой загрузки крупных файлов путем деления на независимые части (Parts) с последующей финальной сборкой манифеста.
* **Transactional Outbox Pattern:** Архитектурный паттерн, при котором доменные события сохраняются в специальную таблицу БД в рамках той же ACID-транзакции, что и бизнес-данные.
* **CDC (Change Data Capture):** Технология непрерывного считывания изменений из лога транзакций БД (WAL) и их публикации в брокер сообщений без нагрузки на основной движок SQL.
* **Database-per-Service:** Принцип архитектуры микросервисов, запрещающий прямое подключение сервиса к базе данных другого сервиса.

## 5. Шпаргалка по теме и концепциям

### 5.1. Принципы проектирования границ сервисов

#### 5.1.1. Критерии декомпозиции микросервисов

| № | Принцип | Суть принципа | Применение в архитектуре S3 |
|---:|---|---|---|
| 1 | **Единый темп изменений (Common Closure Principle)** | Функциональность, которая изменяется по одним и тем же причинам, должна находиться внутри одного сервиса. Изменения одного бизнес-домена не должны требовать модификации несвязанных компонентов. | Изменение бизнес-логики бакетов (`ACL`, квоты, политики доступа) не должно требовать изменения `s3-blob-storage-service`. |
| 2 | **Автономия данных (Database-per-Service)** | Каждый микросервис является единственным владельцем своей базы данных и самостоятельно управляет её схемой. Другие сервисы не обращаются к ней напрямую. | `s3-metadata-service` владеет PostgreSQL с метаданными объектов, а `s3-bucket-service` — собственной БД с конфигурациями бакетов. Между БД запрещены прямые SQL-запросы и JOIN. |
| 3 | **Транзакционные границы (ACID Boundaries)** | Строгая ACID-согласованность обеспечивается внутри транзакционной границы одного сервиса. Межсервисные бизнес-процессы используют асинхронную координацию и итоговую согласованность (Eventual Consistency). | Создание объекта и запись события в Outbox выполняются в одной транзакции PostgreSQL. Передача события в Kafka и обработка подписчиками происходят асинхронно. |
| 4 | **Ограниченный контекст (Bounded Context)** | Каждый сервис определяет собственную предметную модель и отвечает за её интерпретацию. Одинаковые термины в разных сервисах не обязательно означают одинаковые структуры данных. | `Object` в `s3-metadata-service` — это манифест с размером, ETag, версией и ссылками на чанки. В `s3-blob-storage-service` объект представлен физическими байтами чанка, его идентификатором и контрольными суммами. |
| 5 | **Высокая связность внутри сервиса (High Cohesion)** | Функциональность одного бизнес-домена должна быть логически сгруппирована внутри соответствующего сервиса. Компоненты сервиса должны работать на достижение общей бизнес-цели. | Операции создания, удаления и управления версиями объектов относятся к `s3-metadata-service`, а физическое сохранение и восстановление чанков — к `s3-blob-storage-service`. |
| 6 | **Слабая связность между сервисами (Loose Coupling)** | Сервисы должны взаимодействовать через стабильные контракты API и событий, минимально завися от внутренней реализации друг друга. | `s3-event-notification-service` получает события `ObjectCreated` и `ObjectRemoved` через Kafka, не обращаясь напрямую к PostgreSQL с метаданными. |
| 7 | **Независимость развертывания (Independent Deployability)** | Изменение, сборка и развертывание одного сервиса не должны требовать обязательного одновременного развертывания остальных сервисов. | Можно изменить алгоритм проверки ACL в `s3-bucket-service` и развернуть его независимо от `s3-blob-storage-service`. |
| 8 | **Владение бизнес-логикой (Business Capability Ownership)** | Сервис должен владеть законченной бизнес-возможностью, а не просто отдельной CRUD-сущностью или таблицей базы данных. | `s3-bucket-service` отвечает за жизненный цикл бакетов и политики доступа, а не создаёт отдельные сервисы для `ACL`, `Quota` и `BucketConfig`. |
| 9 | **Минимизация синхронных зависимостей (Asynchronous Communication)** | Длительные и не требующие немедленного ответа операции следует выносить в асинхронное взаимодействие, чтобы отказ одного потребителя не блокировал основной бизнес-процесс. | Уведомление внешних систем о создании объекта происходит через Kafka и не должно блокировать успешный `PUT`, если метаданные и Outbox уже зафиксированы. |

#### 5.1.2. Дополнительные архитектурные правила

| Правило | Правильный подход | Антипаттерн |
|---|---|---|
| **Владение схемой БД** | Только сервис-владелец изменяет свою схему и данные. | Несколько сервисов изменяют одни таблицы PostgreSQL. |
| **Межсервисное взаимодействие** | REST/gRPC для синхронных операций, Kafka для асинхронных событий. | Прямые SQL-запросы в чужую БД. |
| **Обмен данными** | Передача DTO и событий с явно определёнными контрактами. | Использование внутренних моделей и ORM-сущностей другого сервиса. |
| **Согласованность** | Outbox, CDC, идемпотентные обработчики, компенсационные операции. | Распределённые транзакции между несколькими БД без необходимости. |
| **Декомпозиция** | Разделение по бизнес-доменам и ответственности. | Отдельный микросервис на каждую таблицу или CRUD-сущность. |
| **Устойчивость** | Таймауты, Retry, Circuit Breaker, Dead Letter Queue. | Неограниченные синхронные цепочки вызовов. |

#### 5.1.3. Ключевые архитектурные критерии

| Критерий | Что необходимо обеспечить |
|---|---|
| **Внутри сервиса** | Высокую связность (High Cohesion). |
| **Между сервисами** | Слабую связность (Loose Coupling). |
| **На уровне данных** | Независимое владение (Database-per-Service). |
| **На уровне транзакций** | Локальные ACID-транзакции и межсервисную Eventual Consistency. |
| **На уровне предметной области** | Чёткие Bounded Context и ответственность за Business Capabilities. |
| **На уровне эксплуатации** | Независимое развертывание и масштабирование. |

**Главный принцип декомпозиции:** микросервисы следует разделять по бизнес-ответственности и границам владения данными, а не по таблицам базы данных, техническим слоям или отдельным CRUD-операциям.

#### 5.1.4. Алгоритм определения границ микросервиса

1. **Определить бизнес-домен:** выявить бизнес-возможность и ответственность будущего сервиса.
2. **Выделить данные:** определить данные, которыми должен владеть сервис, и исключить совместное владение БД.
3. **Определить транзакционные границы:** установить, какие операции должны выполняться в рамках одной ACID-транзакции.
4. **Выявить причины совместного изменения:** сгруппировать функциональность, которая изменяется по одним и тем же бизнес-причинам.
5. **Определить контракты взаимодействия:** выделить синхронные API и асинхронные события для взаимодействия с другими сервисами.
6. **Проверить автономность:** убедиться, что сервис можно независимо разрабатывать, развертывать и масштабировать.
7. **Проверить связность:** убедиться, что внутри сервиса высокая связность, а между сервисами — минимальная необходимая связность.

**Итог:** правильная граница микросервиса проходит там, где заканчивается его бизнес-ответственность, владение данными и транзакционная автономия.


### 5.2. Физический слой хранения чанков

### 5.2.1. Разбиение на чанки и Consistent Hashing
* **Фиксированный размер чанка**: Файлы нарезаются на чанки. Каждая часть получает `chunk_id = SHA-256(chunk_bytes)`.
* **Consistent Hash Ring**: Хэш `Murmur3(chunk_id)` определяет первичную ноду (Primary Storage Node) и две резервные ноды (Secondary Replicas).

### 5.2.2. Репликация и Rack-Awareness
* **Фактор репликации**: RF = 3. Подтверждение записи (ACK) возвращается клиенту только после успешного сохранения чанка на все 3 ноды.
* **Учет топологии**: Primary и Secondary ноды размещаются в разных серверных стойках (Racks) для исключения отказа при падении коммутатора.

### 5.2.3. POSIX Иерархия на файловой системе (`O_DIRECT`)
Запись выполняется в режиме `O_DIRECT / O_DSYNC` в обход Page Cache Linux во избежание latency spikes:

```text
/data/s3chunks/
├── 4a/
│   └── 8f/
│       ├── 4a8f9c12b7...d3.dat   <-- Тело чанка
│       ├── 4a8f9c12b7...d3.meta  <-- Заголовок (CRC32C, ETag, timestamp)
│       └── 4a8f9c12b7...d3.wal   <-- Append-only журнал предзаписи
```

### 5.2.4. Защита от Bit Rot (Integrity Scrubbing)
* **Поблочный CRC32C**: Каждые N КБ данных чанка снабжаются контрольной суммой в `.meta`.
* **Scrubber Demon**: Фоновый процесс сверяет CRC32C с диска и при тихой деградации байт (`CORRUPTED`) автоматического восстанавливает файл с другой реплики.

## 6. Типовые ошибки и антипаттерны

### 1. Shared Database (Общая база данных)
* **В чем ошибка:** Разные микросервисы (`s3-bucket-service` и `s3-metadata-service`) подключаются к одной и той же базе данных PostgreSQL.
* **Почему возникает:** Желание выполнять быстрые SQL JOIN между бакетами и метаданными объектов.
* **Последствия:** Сервисы жестко связываются на уровне схемы БД. Изменение таблицы одним сервисом ломает работу другого.

### 2. Distributed Monolith (Распределенный монолит)
* **В чем ошибка:** Вызов сервиса метаданных требует синхронных цепочек вызовов: Gateway -> BucketSvc -> MetaSvc -> BlobSvc -> NotificationSvc.
* **Почему возникает:** Механический перенос монолитного кода в отдельные сетевые сервисы без перепроектирования связей.
* **Последствия:** Задержки суммируются (High Latency), а надежность системы равен произведению надежностей всех сервисов (если падает NotificationSvc, не работает PUT объектов).

### 3. Entity Services (Микросервис на каждую сущность)
* **В чем ошибка:** Создание микросервисов `ObjectService`, `BucketService`, `TagService`, `ACLService`, `PartService`.
* **Почему возникает:** Ошибка дробления системы по CRUD-сущностям базы данных вместо бизнес-доменов.
* **Последствия:** Огромный избыток сетевых вызовов, распределенные транзакции и сложность поддержки.

### 4. Dual Write на стороне приложения
* **В чем ошибка:** Выполнение `INSERT` в PostgreSQL и вызов `kafkaProducer.send()` прямо из кода микросервиса.
* **Почему возникает:** Незнание паттерна Transactional Outbox или желание сэкономить на настройке CDC.
* **Последствия:** Гарантированная рассогласованность данных при сбоях сети или падении приложения во время записи.

### 5. N+1 Network Calls (Сетевой шторм при скачивании)
* **В чем ошибка:** При выкачивании крупного объекта клиент или Gateway делает отдельный сетевой gRPC-запрос к `s3-blob-storage-service` на каждый 64-килобайтный чанк.
* **Почему возникает:** Отсутствие буферизации и потокового (Streaming) взаимодействия.
* **Последствия:** Процессор расходуется на сериализацию/десериализацию gRPC-кадров, сеть перегружается заголовками.

### 6. Нарушение автономии данных через прямые SQL-запросы
* **В чем ошибка:** `s3-event-notification-service` делает прямой SQL-запрос `SELECT * FROM s3_metadata_db.objects` для обогащения события перед отправкой.
* **Почему возникает:** Желание уменьшить размер событийно-ориентированного конверта (Event Envelope).
* **Последствия:** Сервис уведомлений становится чувствителен к изменениям внутренних таблиц метаданных. Подход ломает принципы Bounded Context.

### 7. Функциональные возможности и фичи системы s3

В этом разделе приведен обзор ключевых архитектурных фич и механизмов распределенного объектного хранилища **s3**, применяемых для управления доступом, жизненным циклом данных, надежностью и безопасностью.

#### 7.1. Версионирование объектов (Object Versioning)

* **Назначение**: Защита от случайной перезаписи или удаления объектов, а также сохранение полной истории изменений файлов.
* **Принцип работы**:
  * Каждая операция `PUT` / `POST` с одинаковым `object_key` не перезаписывает старый файл, а создает новый с уникальным `version_id` (UUID).
  * При запросе `GET` без указания `version_id` возвращается последняя (актуальная) версия объекта.
* **Маркеры удаления (Delete Markers)**:
  * При выполнении вызова `DELETE` файл физически не удаляется: СУБД метаданных создает специальную заглушку `DeleteMarker`.
  * Объект считается "удаленным" для стандартных запросов `GET`, но все предыдущие версии остаются доступны по их явным `version_id`. Физическое удаление происходит только при вызове `DELETE` с указанием конкретного `version_id`.

---

#### 7.2. Политики жизненного цикла и разные уровни хранения (Lifecycle Policies & Storage Tiering)

* **Назначение**: Автоматическое управление временем жизни объектов и оптимизация расходов на хранение за счет перемещения устаревших данных на более дешевые носители.
* **Типы правил (Rules)**:
  * **Transition (Перемещение)**: Автоматическая смена класса хранения по истечении заданного времени от даты создания или модификации.
    * *Hot (Standard)* — быстрые NVMe/SSD накопители для частых операций read/write.
    * *Cool (Infrequent Access)* — более дешевые HDD с сохраненным быстрым latency на чтение, но платой за извлечение.
    * *Cold / Archive (Glacier)* — ленточные накопители или высокоплотные архивы для редкого чтения (задержка восстановления от минут до часов).
  * **Expiration (Удаление)**: Окончательная вычистка старых версий объектов, неактуальных Multipart-частиц или маркеров удаления по достижении TTL (например, через 90 дней).
* **Критерии фильтрации**: Правила применяются по префиксам (`prefix = "logs/2026/"`), тегам объекта (`tag: environment = "temp"`) или количеству устаревших версий.

---

#### 7.3. Управление доступом и безопасность (IAM, Bucket Policies & Pre-Signed URLs)

* **Идентификация и авторизация (SigV4 & IAM)**:
  * Все запросы к API подписываются с использованием алгоритма **AWS Signature Version 4 (SigV4)** на основе паров `Access Key` / `Secret Key`.
  * **Bucket Policies**: Декларативные JSON-политики доступа на уровне всего бакета, определяющие `Principal` (кто), `Action` (`s3:GetObject`, `s3:PutObject`), `Resource` (`arn:aws:s3:::my-bucket/*`) и `Effect` (`Allow` / `Deny`).
* **Временный доступ (Pre-Signed URLs)**:
  * Генерация временных cryptographically-signed ссылок для прямой загрузки или скачивания файлов клиентами без раскрытия секретных ключей.
  * Ссылка содержит встроенный подпись-хеш, набор разрешенных заголовков и жесткий TTL действия (например, 15 минут).

---

#### 7.4. Блокировка объектов и WORM (Object Lock & Retention)

* **Назначение**: Реализация модели **WORM** (*Write Once, Read Many*) для гарантии неизменяемости критически важных данных (финансовая отчетность, аудит, регуляторные требования).
* **Режимы блокировки (Retention Modes)**:
  * **Governance Mode**: Защита от удаления обычными пользователями, однако администраторы с изолированными правами (`s3:BypassGovernanceRetention`) могут снять блокировку.
  * **Compliance Mode**: Жесткая блокировка, которую не может снять **ни один пользователь**, включая суперпользователя root. Объект гарантированно сохраняется до истечения даты `RetainUntilDate`.
* **Legal Hold**: Флаг принудительного удержания (ON/OFF) без даты окончания, применяемый при проведении внутренних расследований или судебных разбирательств.

---

#### 7.5. Составная загрузка (Multipart Upload)

* **Назначение**: Загрузка больших файлов (от 100 МБ до 5 ТБ) частями с поддержкой параллельной передачи и дозагрузки при сбоях сети.
* **Фазы процесса**:
  1. `InitiateMultipartUpload` — регистрация сессии в `s3-metadata-service` и получение `UploadId`.
  2. `UploadPart` — параллельная отправка чанков (part numbers 1..10000, размер от 5 МБ) на ноды хранения с получением `ETag` для каждого чанка.
  3. `CompleteMultipartUpload` — передача манифеста всех загруженных `PartNumber` и `ETag`. Сервис метаданных атомарно собирает финальное представление объекта.
  4. `AbortMultipartUpload` — отмена сессии и фоновая вычистка всех осиротевших чанков с дисков.

---

#### 7.6. Шифрование данных (Server-Side Encryption — SSE)

* **Назначение**: Безопасное хранение данных в покое (Encryption at Rest) для защиты от компрометации физических дисков.
* **Режимы шифрования**:
  * **SSE-S3**: Прозрачное шифрование алгоритмом AES-256 ключами, полностью управляемыми самой платформой хранения.
  * **SSE-KMS**: Шифрование с использованием мастер-ключей из внешнего или встроенного сервиса управления ключами (KMS), с обязательным аудитом вызовов расшифровки.
  * **SSE-C (Customer-Provided Keys)**: Клиент сам передает ключ AES-256 в HTTPS-заголовках к каждому запросу. Сервис использует ключ исключительно в памяти для операции записи/чтения и не сохраняет его на диск.

---

#### 7.7. Межрегиональная репликация (Cross-Region Replication — CRR)

* **Назначение**: Асинхронное дублирование данных между геолокационно удаленными дата-центрами (Region A -> Region B) для обеспечения катастрофоустойчивости (Disaster Recovery) или снижения задержек для пользователей.
* **Механизм работы**:
  * Каждое изменение метаданных (через CDC или топики Kafka `s3.metadata.events`) вычитывается сервисом репликации.
  * Сервис репликации асинхронно копирует чанки объекта в целевой бакет в другом регионе с сохранением `version_id`, исходных временных меток и метаданных.
