### Легенда
**FinGuard Flow** — B2B SaaS-платформа антифрод-мониторинга и мгновенного скоринга транзакций в реальном времени. Платформа выступает «интеллектуальным защитным слоем» между эквайрингом/платежными шлюзами e-commerce компаний и банковскими core-системами.

* **Слушает:** Синхронные REST-запросы на авторизацию платежей от мерчантов и асинхронные вебхуки от платежных шлюзов (Stripe, Adyen, СБП).
* **Оценивает:** Быстрые правила в кэше (Fast Path) и глубокий ML/AML-скоринг с вызовами внешних API (Slow Path).
* **Действует:** Возвращает вердикт (`Approve` / `Reject` / `Challenge`), а при выявлении фрода асинхронно инициирует отзыв авторизации (void), возврат (refund) или блокировку карт в банках.

Пользователи платформы (риск-офицеры) работают с **Real-Time Fraud Dashboard** для отслеживания аномалий в реальном времени.

### Вводные данные для расчетов
* **Клиентов:** 450 финтех-компаний и крупных ритейлеров.
* **Объем данных:** 120 млн транзакций в месяц (~2.5 TB истории при периоде хранения 12 месяцев, включает сырые события, агрегаты и логи аудита).
* **Профиль нагрузки:**
  * **Измеряемый показатель:** Первичные HTTP-запросы авторизации платежей от мерчантов на REST API.
  * Средняя нагрузка: **800 RPS** бизнес-транзакций.
  * Пиковая нагрузка (Черная пятница / распродажи): **12 000 RPS**.
* **Параметры события:**
  * Средний размер события (`TransactionEvent` в формате Avro/JSON): **1.5 KB**.
  * Поток данных в пике: `12 000 * 1.5 KB = 18 MB/сек` (`144 Mbps`).
* **Инфраструктурные лимиты и цели (SLO):**
  * **SLA на авторизацию (Fast Path):** Граница ответа сервера менее 150 мс при целевом `p99 < 100 мс`. *(Примечание: SLA измеряет время обработки внутри инфраструктуры FinGuard Flow и не включает задержки глобальной сети до клиента).*
  * **SLA на глубокий скоринг (Slow Path):** Менее 1.5 сек.
  * **Пропускная способность PostgreSQL OLTP:** Пул из 200 соединений, лимит 2 500 TPS на запись. *(Обоснование: на Fast Path выполняются только 2 быстрых SQL-операции — запись транзакции и Outbox, при 12 000 RPS требуется батчинг Outbox или шардирование; показатель требует подтверждения нагрузочным тестированием).*
  * **Redis Cluster:** Емкость 64 GB (1 Master + 2 Replicas, 30% резерв). Состав данных: кэш лимитов (TTL 1 час), ключи идемпотентности Inbox (TTL 24 часа), sliding window counters.
  * **Лимит внешнего AML API:** **300 RPS** на всю систему.
    * *Расчет конкурентности вызовов AML:* при штатной задержке AML 50 мс для утилизации 300 RPS требуется `300 * 0.05 = 15` параллельных потоков. При деградации AML до 2–4 секунд для сохранения 300 RPS требуется `300 * 3 = 900` параллельных вызовов в ожидании. Увеличение числа воркеров не увеличивает внешнюю квоту в 300 RPS!
  * **Партиционирование Kafka:** Допустимый Consumer Lag — не более 5 000 сообщений (менее 500 мс задержки). 
    * *Предварительная оценка:* `N_partitions = Peak_RPS / Max_Consumer_Throughput = 12 000 / 500 = 24 партиции` *(предварительная оценка с запасом масштабирования, требующая подтверждения нагрузочным тестированием).*
  * **ClickHouse OLAP:** Целевая задержка свежести данных (Data Freshness) менее 1 секунды *(целевой показатель, требующий подтверждения испытаниями).*


### Текущая архитектура «As-Is» (Спроектирована с антипаттернами)

Система развернута как единый монолит за балансировщиком нагрузки. В текущей реализации допущены **8 фундаментальных антипаттернов потоковой обработки**:

1. **Единый монолитный пул ресурсов:** UI, авторизация платежей и тяжелая обработка фоновых задач живут в одном процессе на одном сервере.
2. **Синхронные HTTP-вызовы внутри DB-транзакции:** Внешние вызовы к AML/ML API делаются внутри открытой ACID-транзакции в PostgreSQL.
3. **Dual Write (Двойная запись):** Прямой вызов `kafkaProducer.send()` выполняется в коде сервиса после коммита в БД без использования транзакционного Outbox.
4. **Отсутствие DLQ («Poison Pill»):** Битое событие вызывает обработку исключения без сдвига offset, приводя к бесконечному циклу рестартов и падению Consumer Group.
5. **Внутрипроцессная многопоточность без учета порядка:** Вычитка из Kafka передается в неконтролируемый `ThreadPoolExecutor`, разрушая порядок обработки транзакций одного клиента.
6. **Подмена Event Time на Processing Time:** Оконные агрегации антифрод-правил считаются по системным часам сервера приложения, а не по времени совершения операции на устройстве.
7. **Плохой ключ партиционирования (Hot Partitions):** Партиционирование по `country_code` вызвало катастрофический дисбаланс нагрузки (Hotspot) на отдельных нодах Kafka.
8. **Unbounded State Store:** Отсутствие TTL и регламента очистки состояния в Redis/RocksDB приводит к исчерпанию памяти и долгому восстановлению (RTO) при сбоях.


## 4. Инцидент «Черная пятница»

В час пик распродажи при нагрузке **11 500 RPS** внешний сервис AML-проверок начал отвечать за 4 секунды вместо 50 мс.

Произошел каскадный отказ:
1. Синхронные вызовы удержали транзакции в PostgreSQL -> Мгновенное исчерпание пула соединений (Connection Starvation) -> Падение базы данных.
2. Платежные шлюзы, не получив ответ за 150 мс, начали шторм повторов (Retry Storm).
3. Из-за отсутствия Dual Write защиты при сбое сети события потерялись, а оставшиеся сообщения обработались без идемпотентности, вызвав массовые повторные списания средств у покупателей.
4. Вычитка из Kafka уперлась в тайм-аут `max.poll.interval.ms`, запустив бесконечный **Rebalance Storm**.

## Подсказки и архитектурные рамки

| Вопрос студента | Ответ интервьюера / архитектурная рамка |
| :--- | :--- |
| **«Должен ли Fast Path ждать ответа внешних AML/ML API?»** | **Нет.** Синхронный путь (<150 мс) проверяет только быстрые правила в Redis. Тяжелый скоринг выполняется асинхронно (Slow Path). Приводя вердикт `Approve` до завершения AML/ML, мы осознанно идем на бизнес-компромисс ради соблюдения SLA. При выявлении фрода постфактум инициируется **Post-Charge Recall Protocol**. |
| **«Гарантирует ли Transactional Outbox + Debezium доставку Exactly-Once?»** | **Нет.** Outbox + CDC гарантируют семантику *At-Least-Once* для сообщений. Из-за сетевых повторов Consumer **обязан** использовать Transactional Inbox и устойчивую двухфазную State Machine. |
| **«Достаточно ли сделать `SETNX idempotency_key` в Redis перед началом обработки?»** | **Категорически нет.** Если воркер упадет *после* установки ключа, но *до* фиксации результата в БД, операция навсегда останется в состоянии "Phantom Processing". Нужна таблица состояний (`NEW`, `PROCESSING`, `COMPLETED`, `TEMPORARY_ERROR`, `UNKNOWN_RESULT`, `FAILED`) с fencing tokens и TTL захвата. |
| **«Можно ли добавить salt к account_id (account_id + salt) для устранения Hotspots?»** | **Внимание: Нет для финансовых операций!** Добавление salt случайным образом распределяет события одного аккаунта по разным партициям Kafka и **полностью нарушает гарантию порядка**! Для Hotspot-мерчантов используются предварительная агрегация, dedicated-партиции или виртуальные очереди. |
| **«Устраняет ли `event_version` все конфликты бизнес-операций?»** | **Нет.** `event_version` выявляет устаревшие события (out-of-order), но не устраняет автоматически пропуски версий и конкурирующие изменения. Требуется FSM с буферизацией задерживающихся событий. |
| **«Как избежать Rebalance Storm при задержках внешних API?»** | Вынесите обработку из основного потока `poll()` в локальную ограниченную очередь (`Bounded ArrayBlockingQueue`). При заполнении очереди вызывайте `consumer.pause(partitions)`, продолжая вызывать `poll()` для поддержания heartbeat. Когда очередь освободится — вызывайте `consumer.resume(partitions)`. |
| **«Гарантирует ли Post-Charge Recall заморозку уже списанных денег?»** | **Нет.** Банковские API не гарантируют заморозку проведенных транзакций. Допустимые действия: отмена до клиринга (void), инициирование возврата (refund), или блокировка дальнейших операций по карте. |
| **«Что делать, если внешний API выполнил операцию, но ответ потерялся по таймауту?»** | Перевести транзакцию в состояние `UNKNOWN_RESULT` / `RECONCILIATION_REQUIRED`. Перед повторной отправкой выполнить процедуру сверки (Reconciliation) или передать внешнему API ключ идемпотентности (`Idempotency-Key`). |
| **«Заменяет ли увеличение числа воркеров квоту внешнего API?»** | **Нет.** Лимит 300 RPS является глобальным. Увеличение воркеров без распределенного Rate Limiter (Token Bucket в Redis) приведет лишь к блокировке API-ключа (HTTP 429). |
| **«Как правильно организовать DLQ?»** | Сообщение в DLQ оборачивается в `DLQEnvelope` (payload, error_code, stack_trace, retry_count, timestamp, original_offset). Повторный `Replay` должен быть безопасным благодаря проверке статуса в Transactional Inbox. |
| **«Является ли Fail-Open единственным решением при сбое кэша?»** | **Нет.** Нужна гибкая политика: мелкие платежи low-risk клиентов -> Fail-Open; крупные суммы (>50 000 руб) или high-risk клиенты -> Fail-Closed (`Challenge`/`Reject`). При падении Redis включается фолбэк на локальный In-Memory LRU-кэш пода. |
| **«Обеспечивает ли ClickHouse OLAP транзакционную согласованность?»** | **Нет.** ClickHouse служит для аналитики в реальном времени (Data Freshness < 1 сек). Операционные данные хранятся в PostgreSQL OLTP. |

## Три сценария сбоя

### Сценарий 1: Критический путь, компромиссы Fast Path и обработка отказов (Fast Path, SLA Degradation & Fallbacks)
* **Проблема:** Платформа должна дать вердикт за <150 мс (p99 <100 мс). Внешние AML/ML API отвечают за 2–4 секунды. Выдача `Approve` до завершения скоринга создает окно риска. При сбое Redis или PostgreSQL система рискует полностью заблокировать платежи.
* 💡 **Задания для студентов:**
  1. Разработать политику **Fail-Open vs Fail-Closed** в зависимости от суммы операции, уровня риска и сегмента клиента.
  2. Спроектировать **Post-Charge Recall Protocol**: реальные действия при выявлении фрода постфактум (void, refund, card block) с учетом ограничений банковских API.
  3. Спроектировать механизм деградации при отказе Redis: Circuit Breaker с переключением на локальный In-Memory LRU-кэш пода с бандлом базовых правил.
* 📋 **Требуемые артефакты:**
  * Sequence-диаграмма взаимодействия Fast Path и Slow Path.
  * Таблица фолбэк-режимов при недоступности компонентов (Redis, DB, AML API).
  * Регламент асинхронного отзыва (Recall Protocol).

---

### Сценарий 2: Гарантии публикации, идемпотентность и порядок транзакций (At-Least-Once, State Machine & Order Resolution)
* **Проблема:**
  1. Transactional Outbox + Debezium дают семантику *At-Least-Once*, приводя к дублям при сетевых сбоях. Одиночный `SETNX` приводит к "Phantom Processing" при падении воркера.
  2. Использование `account_id + salt` для сглаживания Hotspots разрушает порядок транзакций по аккаунту!
  3. Сетевые задержки привели к приходу $T_2$ ($12:00:05$) раньше $T_1$ ($12:00:01$).
* 💡 **Задания для студентов:**
  1. Спроектировать **Transactional Inbox** и двухфазный **State Machine** (`NEW`, `PROCESSING`, `COMPLETED`, `TEMPORARY_ERROR`, `UNKNOWN_RESULT`, `FAILED`) с fencing tokens и процедурой сверки (Reconciliation).
  2. Обосновать выбор `account_id` как базового ключа партиционирования. Предложить альтернативные решения для Hotspot-мерчантов без нарушения порядка (выделенные queues, предварительная агрегация).
  3. Разработать алгоритм обработки late-events с использованием `event_version`, Event Timestamp и FSM с буферизацией.
* 📋 **Требуемые артефакты:**
  * Таблица переходов состояний (State Transition Matrix) с SQL-запросами атомарного обновления.
  * Алгоритм работы Transactional Inbox с обработкой состояния `UNKNOWN_RESULT`.
  * Схема партиционирования Kafka и обработчик out-of-order событий.

---

### Сценарий 3: Защита внешних API, управление Kafka Backpressure и DLQ (Rate Limiting, Rebalance Storm Prevention & DLQ Management)
* **Проблема:** Внешний AML API имеет лимит 300 RPS. При всплеске 12 000 RPS медленные вызовы блокируют обработку, превышается `max.poll.interval.ms`, происходит Rebalance Storm. Необработанные сообщения теряются.
* 💡 **Задания для студентов:**
  1. Реализовать схему вычистки из Kafka с использованием ограниченной очереди (`Bounded ArrayBlockingQueue`), механизмов `consumer.pause()` / `resume()` для Backpressure и безопасного завершения (Graceful Shutdown).
  2. Спроектировать глобальный Rate Limiter (Token Bucket на Redis) для соблюдения лимита 300 RPS с учетом всех реплик и ретраев.
  3. Спроектировать структуру `DLQEnvelope` и безопасный регламент повторного проведения событий (**Replay**) через проверку состояния в Transactional Inbox.
* 📋 **Требуемые артефакты:**
  * Схема управления вычисткой Kafka (Pause/Resume/Backpressure Sequence).
  * JSON-схема `DLQEnvelope`.
  * Инструкция для операторов по процедуре Replay из DLQ.
