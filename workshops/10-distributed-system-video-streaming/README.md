# Реверсивный System Design платформы VideoCloud Processing

---

## 1. Учебные цели

В рамках данного кейса рассматриваются следующие концепции распределенных систем:

1. **Разделение контуров реального времени и фоновой обработки:** Изоляция чувствительных к задержкам WebRTC-серверов от тяжелых CPU-емких задач транскодирования, транскрибации и генерации превью.
2. **Архитектура безопасного инджеста медиафайлов:** Отказ от передачи больших видеопотоков через API Gateway в пользу прямой загрузки медиа-чанков в Object Storage (S3) через Presigned URLs.
3. **Изоляция CPU-емких ресурсов и исключение взаимного влияния задач:** Разделение подов REST API и изолированных Auto-Scaling Worker Pools для процессов FFmpeg, чтобы предотвратить сбои Liveness/Readiness Probes и "голодание" пулов соединений.
4. **Управление потоковой обработкой в Kafka и исключение Rebalance Storm:** Использование вынесенных воркеров с локальными ограниченными очередями (Bounded ArrayBlockingQueue) и механизмов `consumer.pause()` / `consumer.resume()` при работе с длительными задачами.
5. **Гарантии порядка кадров и идемпотентное асинхронное объединение:** Партиционирование сообщений в Kafka по `meeting_id` и организация идемпотентного сборщика сегментов с устойчивостью к пропущенным или запоздавшим чанкам.
6. **Отказоустойчивая доставка медиа через CDN:** Построение контура раздачи видео (HLS/DASH) с защитой от эффекта массового одновременного запроса (Thundering Herd / Cache Stampede) с помощью Edge-кэширования и подписи манифестов.

## 2. Бизнес-контекст и вводные данные для расчетов

### Бизнес-контекст
**VideoCloud Processing** - облачный сервис автоматической записи, транскодирования и AI-аналитики видеоконференций и вебинаров. Платформа принимает сырые медиа-потоки от WebRTC SFU-узлов, склеивает чанки записи, перекодирует видео в форматы H.264/AAC (1080p, 720p, 360p), генерирует превью и выполняет AI-расшифровку речи в текст.

### Вводные данные для расчетов
* **Профиль нагрузки:**
  * Средняя нагрузка: **20 000** одновременных конференций с включенной записью.
  * Пиковая нагрузка (вечерние вебинары / мастер-классы): **100 000** одновременных записей.
* **Параметры входящего медиапотока:**
  * Каждая встреча генерирует поток **2.5 Мбит/с** (WebM/Opus+VP8, чанки по 5 секунд ~ **1.56 МБ на чанк**).
  * Суммарный инджест в пике: 100 000 * 2.5 Мбит/с = 250 Гбит/с (~ **31.25 ГБ/сек** входящего трафика).
  * Инджест-события в Kafka: 100 000 встреч / 5 сек = **20 000 RPS** событий о готовых чанках.
* **Нагрузка на просмотр и метаданные:**
  * **15 000 RPS** на получение манифестов записей и просмотр видео после завершения встреч.
* **Инфраструктурные лимиты и целевые метрики уровня обслуживания:**
  * **SLA на публикацию записи:** Готовность HLS-видео к просмотру не более **3 минут** после завершения конференции.
  * **Лимит времени обработки чанка воркером:** Не более 2 секунд на 5-секундный чанк.
  * **Допустимый Consumer Lag в Kafka:** Не более 10 000 сообщений (задержка < 1 секунды на уровне очередей).

## 3. Архитектурный контур и логика WebRTC

Для понимания границы между реальным временем и фоновой обработкой в систему заложен следующий контур WebRTC:

1. **Сигнализация и установление соединения:** 
   * Клиент (браузер / мобильное приложение) через WebSocket подключается к Signaling Service и обменивается SDP-офферами (Session Description Protocol) и ICE-кандидатами для установления DTLS/SRTP сессии.
2. **Передача медиапотока через SFU:**
   * Вместо полного перекодирования на лету для каждого участника (MCU), ноды WebRTC SFU принимают входящие RTP-пакеты от спикеров и дублируют (маршрутизируют) их остальным участникам звонка.
3. **Захват записи на уровне SFU:**
   * При включении записи SFU-узел запускает локальный модуль дампера, который на лету упаковывает входящие RTP-пакеты в 5-секундные медиа-сегменты (файлы `.webm` или `.ts`).
4. **Граница соприкосновения с асинхронным пайплайном:**
   * Запись **не должна** транслироваться через то же соединение, что и клиенты, и **не должна** передаваться прямо в базу данных или API-ноды. 
   * Правильный путь: SFU сохраняет 5-секундный чанк в S3 по Presigned URL и публикует событие `ChunkSavedEvent` в Kafka (`topic: raw-media-chunks`).

---

### Антипаттерны текущей архитектуры

1. **Shared Database (Общая OLTP PostgreSQL):**
   * Сервисы записи, транскодинга, AI-субтитров и дашборды пользователей читают и пишут в единую базу данных PostgreSQL. Блокировки таблиц видеочанков останавливают работу API.
2. **Синхронный прокси-инджест медиафайлов вместо S3 Presigned URLs:**
   * SFU-узлы отправляют большой поток "сырых" видеофайлов по HTTP POST прямо на серверы приложений `Recording Service`. Это приводит к исчерпанию HTTP-сокетов, буферов оперативной памяти (OOM) и I/O-голоданию API.
3. **Колокация CPU-емкого транскодинга и REST API:**
   * Процессы транскодирования FFmpeg запускаются в рамках тех же контейнеров/подов, что и REST API. Загрузка CPU под 100% обрушивает Kubernetes Liveness Probes и вызывает каскадный перезапуск сервисов.
4. **Синхронные HTTP вызовы:**
   * `Transcoder Service` синхронно вызывает `Thumbnail Generator`, а тот синхронно ждет ответа от внешнего `AI Speech-to-Text API`. Замедление внешнего API забивает пулы соединений и полностью останавливает пайплайн.
5. **Kafka Rebalance Storm (Тяжелая обработка в poll loop):**
   * Вызов FFmpeg для сборки видео выполняется непосредственно внутри потока вычистки Kafka Consumer (`poll()`). Время обработки превышает `max.poll.interval.ms`. Kafka считает consumer мертвым, исключает его и уводит кластер в бесконечный Rebalance Storm.
6. **Неверный ключ партиционирования в Kafka:**
   * События чанков отправляются с ключом `chunk_id`. Чанки одного вебинара попадают в разные партиции и вычитываются в случайном порядке. Собрать видео в правильном порядке становится сильно сложнее.
7. **Отсутствие DLQ и обработки битых кадров:**
   * Поврежденный видеокадр вызывает неопределенное исключение FFmpeg. Без Dead-Letter Queue воркеры зацикливаются на сбойном сообщении, блокируя продвижение offset для всего вебинара.
8. **Эффект массового одновременного запроса при отдаче видео клиентам:**
   * При завершении вебинара 100 000 зрителей мгновенно открывают ссылку на запись. Из-за отсутствия CDN и кэширования HLS-манифестов все клиенты создают нагрузку на базу данных и S3 Origin.

## 4. Инцидент «Вебинар-миллионник»

В 19:00 начинается трансляция главного вебинара года (100 000 участников, 50 SFU-нод записывают видеопотоки). 

### Хронология катастрофы
1. **19:05:** SFU-ноды начинают синхронно слать 5-секундные бинарные чанки (~ 31 ГБ/с) по HTTP POST на API-серверы. Память подов заполняется буферами, серверы уходят в OOM (Out of Memory).
2. **19:08:** Оставшиеся ноды запускают фоновые процессы FFmpeg. CPU загружается на 100%. Kubernetes убивает ноды по таймауту Liveness Probe.
3. **19:12:** Фоновые воркеры Kafka не успевают уложиться в `max.poll.interval.ms` из-за тяжелого транскодинга. Начинается каскадный Rebalance Storm — обработка записей всех встреч полностью останавливается.
4. **19:15:** Внешнее AI Speech API превышает лимит в 100 RPS и возвращает `HTTP 429 Too Many Requests`. Синхронная цепочка сервисов провисает, блокируя соединения к PostgreSQL.
5. **19:20:** Пользователи пытаются открыть записи прошедших утренних встреч. 15 000 RPS обрушиваются на лежащую PostgreSQL. Система полностью недоступна.

## 5. Подсказки

| Вопрос                                                                       | Ответ интервьюера                                                                                                                                                                                                      |
|:-----------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Должен ли SFU-узел передавать видеофайлы через наш REST API?**             | **Категорически нет.** Видеофайл должен напрямую загружаться в S3 через Presigned URL. REST API должен обрабатывать только легкие JSON-метаданные.                                                                     |
| **Можно ли запускать FFmpeg прямо в контейнере приложения?**                 | **Нет.** Процессы транскодирования должны быть вынесены в отдельные изолированные Worker Pools с чёткими cgroups (CPU/RAM limits), запускаемые на dedicated spot-нодах.                                                |
| **Как предотвратить Rebalance Storm при тяжелой обработке видео?**           | Вынесите FFmpeg-обработку из основного потока `poll()` в локальную ограниченную очередь (`Bounded ArrayBlockingQueue`). При заполнении вызывайте `consumer.pause(partitions)`, сохраняя вызовы `poll()` для heartbeat. |
| **Какой ключ партиционирования использовать для видеочанков?**               | Ключом **обязан** быть `meeting_id`. Это гарантирует, что все чанки конкретной встречи попадут в одну партицию и будут обработаны строго последовательно.                                                              |
| **Что делать, если внешний AI-сервис субтитров падает или отдает HTTP 429?** | AI-субтитры - это некритичный путь (Slow Path). Транскодирование видео **не должно** ждать AI. Запустите асинхронный процесс через отдельный топик Kafka с Circuit Breaker и Rate Limiter.                             |
| **Как защитить базу данных при выходе видеозаписи в топ просмотров?**        | Раздача видео (HLS `.m3u8` и `.ts` segments) должна производиться через CDN (примеры: CloudFront/Fastly) с подписью ссылок через Signed Cookies / Signed URLs.                                                         |

## 6. Сценарии сбоя

---

#### Сценарий 1: Высоконагруженный инджест, изоляция вычислений и обработка битых кадров

* **Контекст инцидента:**  
  В пик вебинара 100 000 SFU-узлов генерируют входящий медиапоток **31.25 ГБ/с** (20 000 RPS). Передача файлов по HTTP POST на API-серверы вызывает OOM. Отдельные SFU передают поврежденные WebM-файлы («битые» заголовки кодека): FFmpeg зацикливается, загружает CPU на 100%, а Liveness Probes Kubernetes каскадно обрушивают ноды приложения.

* **Задание:**
    1. **Спроектировать схему прямой загрузки:** Безопасный инджест чанков в S3 через Presigned URLs / Multipart Upload в обход API Gateway (контроль TTL, размера и `Content-MD5`).
    2. **Спроектировать изолированный контур транскодирования:** Автомасштабируемый пул воркеров на Spot-нодах с cgroups-лимитами CPU/RAM и Graceful Shutdown.
    3. **Реализовать обработку поврежденных кадров:** Изоляция процесса FFmpeg с Execution Timeout и маршрутизация битых чанков в карантинный S3-баккет и топик Dead-Letter Queue (DLQ).

* **Требуемые артефакты:**
    * **Sequence-диаграмма:** Взаимодействие SFU-узла, API авторизации, S3 и Kafka.
    * **Схема данных DLQ Envelope:** JSON-схема структуры сообщения в DLQ (код ошибки FFmpeg, `meeting_id`, `chunk_index`, S3-ссылка, трассировка).

---

#### Сценарий 2: Потоковая сборка HLS в Kafka при неверном порядке чанков и защита от Rebalance Storm

* **Контекст инцидента:**  
  Сетевые задержки при загрузке в S3 привели к вычитыванию чанков из Kafka в неверном порядке, ломая временную структуру HLS-видео. Длительное транскодирование превышает `max.poll.interval.ms`: Kafka считает воркеры мертвыми и вводит кластер в бесконечный Rebalance Storm.

* **Задание:**
    1. **Спроектировать партиционирование и детерминированную сборку:** Партиционирование по `meeting_id` и скользящее окно сборки (Sliding Window Assembler) на стороне воркера для сортировки чанков перед FFmpeg.
    2. **Реализовать безопасный паттерн вычистки Kafka:** Разделение вычитки (`poll()`) и обработки через Bounded ArrayBlockingQueue с вызовами `consumer.pause()` / `resume()` для сохранения Heartbeat.
    3. **Проработать сценарий выпавших кадров:** Логика таймаутов ожидания и генерация компенсирующих пустых кадров (черный экран/тишина) без зависания конвейера.

* **Требуемые артефакты:**
    * **State Machine диаграмма:** Состояния сборщика (`WAITING_FOR_CHUNK`, `BUFFERING`, `FLUSHING_TO_FFMPEG`, `MISSING_CHUNK_TIMEOUT`).
    * **Матрица крайних случаев:** Алгоритм обработки потери первого/последнего чанка и дубликатов.

---

#### Сценарий 3: Отказоустойчивая раздача HLS через CDN, защищенное кэширование и асинхронный AI-пайплайн

* **Контекст инцидента:**  
  После публикации ссылки 15 000 зрителей перегрузили PostgreSQL и S3 запросами плейлистов `.m3u8` из-за отсутствия CDN и кэша. База упала от исчерпания соединений. Синхронный вызов стороннего AI-API субтитров отдал `HTTP 429 Too Many Requests`, заблокировав публикацию видео и вызвав ошибки 500 у пользователей.

* **Задание:**
    1. **Спроектировать раздачу медиаконтента:** Топология раздачи через CDN (CloudFront) с правилами кэширования плейлистов/сегментов и авторизацией доступа через Signed URLs / Cookies.
    2. **Защита от эффекта Thundering Herd / Cache Stampede:** Двухуровневое кэширование метаданных в Redis (Cache-Aside) с распределенными блокировками (Redis Mutex / Singleflight).
    3. **Разделить быстрый и медленный пути:** Мгновенная публикация HLS-видео без ожидания AI-субтитров. Вынос AI-транскрибации в асинхронный контур с Rate Limiter (100 RPS) и Circuit Breaker.

* **Требуемые артефакты:**
    * **Схема сетевой топологии раздачи:** Маршрутизация запроса: CDN Edge -> Origin Shield -> Redis -> S3 / PostgreSQL.
    * **Псевдокод кэширования:** Защита от Cache Stampede при запросе метаданных с использованием Redis Mutex / Singleflight.
    * **Спецификация событийного контура:** Схема состояний видео (`RECORDED` -> `TRANSCODED_READY` -> `AI_SUBTITLES_PROCESSING` -> `FULL_ENRICHED`) и структура событий Kafka.

## 7. Глоссарий терминов

* **WebRTC:** Протокол связи реального времени между браузерами и серверами для передачи аудио и видео с низкой задержкой (<500 мс).
* **SFU:** Архитектурный узел WebRTC, который принимает медиапоток от вещателя и перенаправляет (дублирует) его зрителям без переделки кодека.
* **Presigned URL:** Временная безопасная ссылка, сгенерированная S3, позволяющая клиенту напрямую загрузить файл в S3 в обход бэкенд-серверов.
* **HLS:** Протокол потоковой передачи видео на основе HTTP, разбивающий видео на `.m3u8` плейлисты и 2–10 секундные `.ts` медиа-сегменты.
* **Транскодирование:** Процесс декодирования сжатого видеопотока и его повторного кодирования в другие разрешения (1080p, 720p) и кодеки (H.264, AAC).
* **Rebalance Storm:** Состояние кластера Kafka, когда длинные задачи вызывают регулярное исключение воркеров из Consumer Group, вызывая непрерывную перераспределительную блокировку.
* **Resource Contamination:** Антипаттерн, при котором тяжелые фоновые вычисления (FFmpeg) выполняются в той же среде, что и критичные к задержкам сервисы (REST API).
* **Cache Stampede / Thundering Herd:** Сбой, возникающий при одновременном обращении тысяч клиентов за истекшим ключом кэша напрямую в БД.

## 8. Шпаргалка по архитектуре обработки видео

```
[SFU WebRTC Node]
       │ (1. Request Upload URL)
       ▼
[Recording API] ──► (Generates Presigned URL) ──► Returns URL to SFU
       │
       │ (2. Direct Upload 31 GB/s)
       ▼
[S3 Object Storage (Raw Chunks)]
       │
       │ (3. Publish Event: ChunkSaved, Key = meeting_id)
       ▼
[Kafka Cluster (topic: raw-chunks)]
       │
       │ (4. Pause/Resume Safe Worker Loop)
       ▼
[Transcoder Worker Pool (Isolated CPU / Spot Nodes)]
       │
       ├─► (5. Assembly & FFmpeg HLS Rendering) ──► [S3 Storage (HLS Videos)]
       │                                                     │
       └─► (6. Async AI Event) ──► [AI Worker + RateLimiter] │ (7. Distribute)
                                                             ▼
                                                    [CloudFront / CDN] ◄── [Viewers]
```

### Золотые правила проектирования
1. **Никакого медиатрафика через API Gateway:** Бинарные файлы идут только напрямую в S3 по Presigned URLs.
2. **Изоляция FFmpeg:** Никакого FFmpeg на Web-нодах! Только изолированные Worker-поды с ограниченными cgroups.
3. **Строгий порядок по meeting_id:** Сообщения одной встречи живут в одной партиции Kafka.
4. **Защита Kafka Consumer:** Тяжелая обработка должна выноситься из `poll()`, с использованием `pause()` и `resume()`.
5. **Раздача через CDN:** Метаданные плейлистов HLS кэшируются на Edge-нодах, защита базы через Redis Cache-Aside.
